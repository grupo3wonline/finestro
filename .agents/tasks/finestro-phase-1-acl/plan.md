## Decisions

1. **403 vs 404 convention**: a record that exists but belongs to another user (and the user is not an accepted shared-wallet member) → **404** (existence is not disclosed; matches existing tests and the scoped lookups). A user acting on their *own* data, or on a list/create route, without the required Spatie permission/role → **403**. Policies implement this with `Response::denyAsNotFound()` for ownership and `Response::deny(...)` for permissions.
2. **Spatie tables keep Spatie's bigint IDs** (`roles`, `permissions` are framework/lookup tables like `jobs`/`cache`); only `model_id` becomes `uuid` to reference users. No SoftDeletes on them. Documented in the audit as an explicit exception to the UUID/SoftDeletes rule.
3. **Permissions are about ACL, not plans.** Plan limits (`hasFeature`, `canCreate`, `CheckPlanLimit`) stay exactly as they are (Phase 2). Permission set (guard `web`): `wallets.{view,create,update,delete}`, `transactions.{view,create,update,delete}`, `goals.{view,create,update,delete}`, `budgets.{view,create,update,delete}`, `categories.{view,create,update,delete}`, `reports.view`, `reports.export`, `ai.use`, `admin.access`. Role `user` = everything except `admin.access`; role `admin` = everything. Admins do **not** bypass ownership (no `Gate::before`): an admin still gets 404 on another user's record.
4. **Policies are the single decision point** (ownership + permission). One abstract `OwnedResourcePolicy` holds the shared logic (`$permissionPrefix`), concrete policies extend it. Permission check uses `$user->checkPermissionTo('x.y')` (returns false instead of throwing when the permission row is missing). Abilities are named `view/update/...`, never the same string as a permission, so Spatie's Gate hook does not interfere.
5. **Shared wallets**: an accepted member (`wallet_members.accepted_at` not null, not soft-deleted) may **view** the wallet (`wallets.show`) and see it in "Carteiras Compartilhadas Comigo". Edit/update/delete/invoice/pay-invoice and posting transactions stay **owner-only** in Phase 1 (member editor rights and showing the owner's transactions to members are deferred and documented). Pending/unrelated users → 404.
6. **Legacy `role` column** stays (readable, DB default `'user'`) for backward compatibility; authorization no longer reads it. The seeder maps it once. `CheckRole` middleware is deleted and the `'role'` alias points to Spatie `RoleMiddleware`; `'permission'` and `'role_or_permission'` aliases are added.
7. **Store requests** authorize with `can('create', Model::class)` (403 on missing permission). Record actions authorize in the controller after the scoped lookup (`abort(404)` when null, then `$this->authorize(...)`). Validation for Update requests runs before the ownership check; that is acceptable because every FK in those rules is already owner-scoped (`ownedWalletRule`/`ownedCategoryRule`), so a 422 leaks nothing.
8. **Tests get roles automatically**: base `Tests\TestCase` sets `protected $seed = true; protected $seeder = RolesAndPermissionsSeeder::class;` (honoured by `RefreshDatabase`), and `UserFactory::configure()` assigns role `user` via `Role::findOrCreate('user', 'web')` so factories work even without the seeder.
9. **No FEAT decomposition**: this is one coherent security change whose parts (ACL → policies → controllers → tests) depend on each other in sequence; the existing code/review loop runs this plan.
