# Phase 11 UI refactor, security hardening, and test coverage expansion

Phase 11 applied three parallel workstreams to Finestro: (1) landing page persuasion triggers and glassmorphism/neumorphism styling on the dashboard and calculators; (2) `declare(strict_types=1)` audit of auth/feature controllers, extraction of `payInvoice` inline validation to a dedicated `PayInvoiceRequest`, and honeypot protection on the login form; (3) 14 new test files covering CRUD flows, API v1, security vectors, calculator/simulator smoke tests, and unit tests for core services. Composer test records 1113 tests — 1098 pass, 15 skip, 0 fail. `npm run build` exits 0.

Watch for: duplicate BreadcrumbList JSON-LD on the four public legal/FAQ pages (confirmed); `composer analyse` full-suite fails with a pre-existing PHPStan internal error on `CreditCardInvoiceService.php` — a file not touched by Phase 11 (confirmed, pre-existing).

**Verdict**: APPROVED

## High-level view

The `PayInvoiceRequest` resolves the route parameter defensively as `$this->route('wallet') ?? $this->route('id')`, guarding against a name mismatch between the `{wallet}` route segment and the controller's `string $id` parameter. This is worth noting because the controller still uses `$id` — it works via Laravel's positional binding, but inconsistency between the route parameter name and the method signature is a maintenance hazard.

FEAT-002 introduced a `breadcrumbs()` method with `name+url` keys alongside the pre-existing `breadcrumbList()` method which uses `label+url` keys. These serve different callers: `breadcrumbs()` is called from `@push('jsonld')` on individual pages, while `breadcrumbList()` is called by the `x-ui.breadcrumb` component. Pages that use both a breadcrumb component and a pushed `breadcrumbs()` call emit two BreadcrumbList JSON-LD schemas — one in `<head>`, one inline in `<body>`. All four legal/FAQ pages (privacy, terms, cookies, faq) have this duplication as a result of FEAT-002 not accounting for the breadcrumb component's own JSON-LD output.

`composer analyse` fails with a pre-existing PHPStan internal error on `CreditCardInvoiceService.php` (phar stub path resolution). FEAT-002 documented this and worked around it by analysing changed files individually, but the full `composer quality` pipeline cannot run end-to-end. The PHPStan baseline remains at 3 entries, unchanged from prior phases.

The strict_types audit was deliberately narrowed to 14 high-risk files (auth controllers + 5 feature controllers). Dozens of pre-existing files still lack the declaration: 5 DTOs, 4 Traits, 5 Store FormRequests, several middleware and console commands. The project-wide `contribution_requirements` say every PHP file must have it; this phase closes the most critical surface and defers the rest.

## Duplicate BreadcrumbList schemas on legal pages

`seo-head.blade.php` renders `@stack('jsonld')` inside `<head>`. The `x-ui.breadcrumb` component also calls `StructuredDataService::breadcrumbList()` and emits a `<script type="application/ld+json">` inline wherever the component is placed in the page body. The four legal pages do both: they push a `breadcrumbs()` block to the stack and include `x-ui.breadcrumb` in `@section('content')`. The two schemas use slightly different internal key names (`name` vs `label`) but produce identical JSON-LD output. Google handles multiple JSON-LD blocks per page, so this is not a functional bug, but it is wasteful and indicates the breadcrumb component's JSON-LD output was not accounted for when FEAT-002 designed the push pattern.

## PHPStan environment block

`composer analyse` exits non-zero on `CreditCardInvoiceService.php` with a phar stub path resolution error. This file was not touched by Phase 11. FEAT-002 verified all changed files individually at level 6 with zero errors, and the baseline remains at 3 entries. Until the root cause is resolved or baselined, the full `composer quality` gate fails, meaning regressions in files not part of this phase could go undetected in future runs.

## Strict_types coverage gap

The project-wide requirement in `context.json` says "every PHP file must have declare(strict_types=1)". The 14 files targeted by FEAT-002 all have it. Pre-existing files that do not include DTOs (5 files), core Traits (HasUuid, BelongsToUser, Filterable, LogsOwnedActivity), Store FormRequests (5 files), TransactionRules concern, StripeSetup and ProcessRecurringTransactions commands, SecurityHeaders and EnsureTermsAccepted middleware, and FinancialReportMail. These files were not touched by Phase 11, so they are outside this review's scope, but the gap between the stated requirement and reality should be tracked.

## Tooltip component ARIA gap

`x-ui.tooltip.blade.php` renders a `role="tooltip"` div that shows on CSS `group-hover`. The component wraps an arbitrary slot as the trigger, so it cannot statically inject `aria-describedby` onto the trigger without knowing its structure. As delivered, the tooltip is visually functional but not announced by screen readers. This affects all four wallet form fields that use the component. Mitigating options include: (a) adding a `$id` prop and rendering the trigger slot inside a wrapper with `aria-describedby`, or (b) switching to an Alpine.js implementation where the id can be generated and injected dynamically.

## Route parameter name inconsistency

`payInvoice` route uses `{wallet}` but `WalletController::payInvoice()` accepts `string $id`. Laravel resolves this via positional binding for primitive types — not by name — so the wallet UUID does arrive in `$id`. The `PayInvoiceRequest` explicitly handles this mismatch with `$this->route('wallet') ?? $this->route('id')`. Both the inconsistency and the workaround pre-date Phase 11; FEAT-002 touched the method but did not align the parameter name. It's a low-risk maintenance debt: a future rename of the route segment would silently break the FormRequest guard.
